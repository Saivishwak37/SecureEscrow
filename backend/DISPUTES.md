# Dispute creation identity limitation

The current demo has no authenticated backend session or signed identity token. The frontend sends the selected demo user's `actorId` with the dispute request, matching the identity convention used by the existing escrow actions. The API checks that this ID is a participant in the specified escrow, but a direct API caller can still choose either participant's ID. This is a demo authorization check, not production authentication. Dispute creation freezes the escrow as described below.

## ER diagram alignment

The diagram's `DISPUTE` entity has `dispute_id`, `escrow_id`, optional `milestone_id`, `raised_by`, `reason`, `status`, `created_at`, `updated_at`, and `resolved_at`. The Step 1 creation form additionally requires structured title, category, and requested resolution values. The user approved adding `title`, `category`, and `requested_resolution`; the submitted description is stored in the diagram's existing `reason` field. Runtime JavaScript uses the repository's `id` and camelCase naming conventions. Step 1 does not add condition or transaction links, assignment, or any of the other dispute entities.

## Step 2 freeze behavior and limits

Creating a dispute now synchronously creates the dispute record, records an `escrowStatusHistory` entry, and changes the escrow status to `DISPUTED`. If either transition write fails, the in-memory code rolls back the preceding write. The history collection follows the ER diagram's `ESCROW_STATUS_HISTORY` fields, using the current repository's `id`/camelCase conventions. Freezing does not create a transaction or ledger entry.

Escrow service release/funding paths, transaction creation for `FUND`/`RELEASE`/`REFUND`, escrow-account ledger debits, milestone status synchronization, and escrow status updates reject or preserve an unresolved dispute. The application has no automatic release job and no refund endpoint today; deadline evaluation only satisfies its condition. The transaction and ledger service guards also cover those operation types for future callers.

Operations in this repository are synchronous and stored in one Node.js process. The concurrent dispute/release test confirms that these synchronous operations serialize within that process, but separate workers/processes or persistent databases would need transactional locking/constraints. No production-grade multi-process concurrency guarantee is claimed.

## Step 3 evidence storage

`DISPUTE_EVIDENCE` follows the diagram fields (`evidenceId`, `disputeId`, `uploadedBy`, `type`, `description`, `createdAt`) using runtime `id`/camelCase names. The approved metadata extension adds `fileName`, `storageKey`, `mimeType`, `fileSize`, and `fileHash`; `storageKey` is internal and is omitted from API responses. Upload bytes are stored under `backend/uploads/dispute-evidence` by default, configurable with `DISPUTE_EVIDENCE_STORAGE_DIR`. The maximum upload size defaults to 5 MiB and is configurable with `DISPUTE_EVIDENCE_MAX_FILE_SIZE_BYTES`.

This local filesystem store is temporary development storage: it is not durable across deployments or shared between multiple application instances, and metadata remains in memory. Production should use durable object storage and persistent metadata. The demo actor ID used for participant/admin authorization is also client-supplied and is not authentication.

## Step 4 dispute messaging

`POST /api/disputes/:disputeId/messages` accepts `{ actorId, message }`; `GET /api/disputes/:disputeId/messages?actorId=...` returns chronological messages with a limited sender summary (`id`, `name`, and `type`). Messages use the runtime `id`/camelCase convention for the diagram's DISPUTE_MESSAGE fields and are held in a dedicated in-memory repository. `DISPUTE_MESSAGE_MAX_LENGTH` configures the message limit (default 5000 characters). Messages can be sent while the dispute is active, do not edit existing messages, and do not perform escrow or financial operations. Client-supplied actor IDs are checked against the escrow's participants, or against the seeded demo admin identity for admin access; without authenticated sessions/tokens, callers can impersonate a known demo identity. In-memory messages are lost when the process resets.

## Steps 6 and 7: resolution and audit

No ER diagram file was present in the workspace. The runtime follows the entity and field names supplied in the Step 6 request and the repository's `id`/camelCase conventions: `disputeResolutions` represents `DISPUTE_RESOLUTION`, `disputeResolutionAllocations` represents `DISPUTE_RESOLUTION_ALLOCATION`, and `disputeStatusHistory` represents `DISPUTE_STATUS_HISTORY`. No entity was duplicated. Resolution records add `transactionIds` (split decisions create two transactions while the diagram specifies one `transactionId`), `executionStatus`, `remainingEscrowBalance`, and an `idempotencyKey` plus request fingerprint to support safe retries and partial releases. Allocation rows carry a `transactionId` so each amount can be reconciled with the actual transfer. These extensions should be incorporated into the ER diagram when it is available.

`POST /api/disputes/:disputeId/resolve` accepts `actorId`, `decision`, `reasoning`, `idempotencyKey`, and the relevant `providerAmount`/`clientAmount`. Recipients are derived from the escrow's Client and Provider accounts; client-supplied recipient account IDs are ignored. A dispute tied to a milestone resolves only that milestone's available funds and leaves other milestones usable. `PATCH /api/disputes/:disputeId/status` is an admin-only transition API. Associated escrow participants and admins can read `GET /api/disputes/:disputeId/history?actorId=...` and `GET /api/disputes/:disputeId/resolutions?actorId=...`; only admins can change status or execute a resolution.

The lifecycle statuses are `OPEN`, `EVIDENCE_SUBMISSION`, `UNDER_REVIEW`, and `RESOLVED`. Admin transitions may move OPEN to evidence submission or review, evidence submission to review, and review back to evidence submission. Resolution closes the dispute only when the escrow's tracked available balance reaches zero. A partial release credits the Provider, leaves the escrow `DISPUTED`, and moves the dispute to `UNDER_REVIEW`; further admin resolution calls can allocate the remaining balance. A final Provider-only payout closes the escrow as `RELEASED`, a Client-only refund closes it as `CANCELLED`, and a split closes it as `RESOLVED`. Normal release/refund paths remain guarded while funds remain disputed.

Resolution uses the existing transaction and double-entry ledger services. The controlled internal transfer path repeats the admin, dispute, escrow, recipient, account type, and currency checks; it is not exposed as a general request flag. Resolution runs synchronously in one Node.js process and snapshots/restores the in-memory collections if a transaction, ledger, allocation, audit, or state write throws. The failure is then recorded in dispute status history when possible. This prevents partial writes within this process. It does not provide cross-process locking or durable transactions. The old escrow-only resolver now rejects attempts to unfreeze without financial allocation.

Resolution idempotency keys are unique per dispute and admin. A repeated request with the same key and same request data returns the original resolution; reuse with different data is rejected. A new key permits a follow-up allocation after a partial release. All resolution decisions and status transitions retain their audit records; evidence and messages remain stored after resolution. In-memory data is lost on process restart. Demo `actorId` values remain client-supplied and are not production authentication.
